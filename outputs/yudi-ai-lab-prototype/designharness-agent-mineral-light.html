Design Harness Agent

面向 AI 智能体的产品设计与设计工程工作流系统

优质、高效、可控的 AI 产品设计 =

正确的产品判断 可控的设计过程 可继承的业务上下文 可验收的交付结果

普通 LLM 负责生成，通用 Agent 工作环境负责执行，而 DesignHarnessAgent 负责定义产品设计应该如何推进，以及怎样才算真正完成。它通过知识契约、状态化工作流和 Human-in-the-loop 决策机制，把产品设计过程中的知识、判断、设计与证据沉淀为可持续继承的产品资产。

02 / PROBLEM

产品设计真正容易失控的，
是判断失去连续性

产品设计不是一次内容生成，而是一组跨任务、跨角色、跨阶段持续发生的判断。

当任务边界、已确认决策、人机责任和完成标准无法稳定继承时，局部输出即使正确，整体产品仍然可能失控。

01 任务边界断裂
发生了什么

一次对话被当成一个完整任务，不同目标、约束和需求逐渐混在一起。

业务后果

任务范围持续漂移，输出看似完整，却可能已经偏离真正要解决的问题。

02 决策连续性断裂
发生了什么

已经确认的方向、取舍依据与验收标准，只存在于临时对话中。

业务后果

新任务不断重复旧讨论，甚至在没有明确决策的情况下覆盖已有结论。

03 人机责任边界断裂
发生了什么

关键产品判断与一般执行任务没有被明确区分。

业务后果

AI 可能越过需要人确认的决策，也可能在普通执行节点频繁打断工作。

04 完成标准断裂
发生了什么

文档、页面或代码已经生成，但缺少稳定的验收定义和完成证据。

业务后果

“已经生成”被误认为“已经完成”，结果无法被验证，也难以安全交给下游。

COMMON ROOT CAUSE 它们不是四个独立问题，而是同一个系统问题：产品设计缺少一套能够跨任务维持判断连续性的专业工作协议。

DesignHarnessAgent 因此不从“生成更多内容”开始，而从任务身份、权威状态、决策边界与验收闭环开始。

04 / PRODUCT KNOWLEDGE

让 AI 理解产品，而不只是生成文档

四个能力集群不是瀑布式审批流程，而是一组能够互相调用、校验、回填和编译的产品知识接口。

产品知识 Product Knowledge

商业分析

Why

梳理业务流程、价值链、用户 / 客户 / 角色关系、商业约束和成功机制。

业务模型

What

建立业务对象画像、业务字典、对象关系、业务动作、状态流转、业务规则和权限策略。

产品表达

Experience

把抽象业务模型转化为用户可理解、可操作的产品结构和状态表达。

需求表达

Delivery

把产品知识切成一次可开发、可验收、可追踪的交付范围。

四个能力集群之间更像 API，而不是审批门。

商业、业务、体验和交付信息会互相回填，而不是从上到下机械流转。这个结构让 AI 可以在新任务中恢复已知产品语义，并保持后续设计判断一致。

06 / DESIGN ASSETS

让设计方向有依据，而不是靠 AI 即兴发挥

Reference Library 与 Color Card Registry 将容易依赖主观感觉的设计判断，转化为有语义、有适用条件、有使用代价、可以被人确认并被 Agent 复用的设计资产。

01
任务上下文 目标终端、页面类型、内容密度、交互复杂度、用户成熟度。
02
Reference Library 不是收藏网站缩略图，而是可检索的视觉决策知识层。
03
提取设计特征 层级、密度、操作区、引导方式、信息节奏与状态表达。
04
转译为业务方向 效率工作台、引导式助手、内容探索、低噪音数据工具。
05
用户确认 确认的不是某个网站风格，而是方向适配、借鉴点和使用代价。

COLOR CARD REGISTRY

色卡是一种设计知识对象

用户确认的不是 HEX 或 RGB，而是色彩气质、适合场景、产品语义和使用代价。

产品气质
清晰、克制、可信，适合复杂产品设计与效率工作台。
适用场景
数据工具、B 端控制台、设计工程工作流、低噪音分析页面。
使用代价
需要更严格的信息优先级，不适合高情绪营销场景。
索引标签
clear / restrained / B2B / system / evidence

DesignHarnessAgent 关注的不是让 AI 生成更多内容， 而是让 AI 在清晰的任务身份、产品语义、人类决策边界和验收协议中，稳定参与真实产品开发。
